# Documentation

This folder holds the design, policy, and research documentation for our submission to the Factored AI & Data Hackathon 2026: an AI-first customer service system for **transaction-dispute intake** at a synthetic LATAM bank.

## Structure

```
docs/
├── README.md                  # This index and the documentation conventions
├── glossary.md                # Shared terminology used across all documents
├── dispute-policy.md          # Normative dispute-intake policy (rules, thresholds, actions)
├── spikes/                    # Time-boxed investigations and their findings
│   └── 2026-09-25-data-label-validity.md
└── diagrams/                  # One topic per file: a .md explanation plus its generated .svg
    ├── dispute-decision-flow.md
    ├── dispute-decision-flow.svg
    ├── dispute-case-lifecycle.md
    └── dispute-case-lifecycle.svg
```

| Category | Folder | Purpose |
|---|---|---|
| Documents | `docs/` | Normative or descriptive documents that define how the system behaves. |
| Spikes | `docs/spikes/` | Investigations that answer a specific question with evidence. Spikes inform decisions but do not define behavior. |
| Diagrams | `docs/diagrams/` | Visual views of behavior defined in documents. A diagram never introduces a rule that is not in a document. |

## Conventions

### Language and format

- All documentation is written in English, in GitHub-flavored Markdown.
- Diagrams are SVG files generated by `scripts/render_diagrams.py` on a fixed grid: one start, one end, orthogonal lines, and no line crossing a node. Each SVG is embedded in a `.md` file that explains it. Edit the script, never the SVG.
- Customer-facing text examples are given in Spanish (`es`) and Portuguese (`pt`), the two languages the system supports.

### Document header

Every document starts with its title followed by this metadata table:

| Field | Meaning |
|---|---|
| Status | `Draft`, `Accepted`, `Superseded`, or `Complete` (spikes only). |
| Version | Semantic version of the document. Increment the minor version for additive changes and the major version when a rule changes meaning. |
| Last updated | ISO 8601 date (`YYYY-MM-DD`). |
| Related | Links to documents this one depends on or informs. |

### Normative keywords

Policy documents use **MUST**, **MUST NOT**, **SHOULD**, and **MAY** as defined in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119). Anything not marked with one of these keywords is explanatory.

### Identifiers

Rules and parameters carry stable identifiers so that code, audit logs, tests, and documents can reference the same thing.

| Prefix | Used for | Example |
|---|---|---|
| `GATE-nn` | Preconditions evaluated before any dispute can proceed | `GATE-02` |
| `ESC-nn` | Mandatory escalation triggers | `ESC-01` |
| `ACT-nn` | Action permissions and confirmation requirements | `ACT-03` |
| `COM-nn` | Customer communication rules | `COM-02` |
| `DATA-nn` | Data handling and fairness rules | `DATA-01` |
| `RC_*` | Dispute reason codes | `RC_DUPLICATE` |
| `UPPER_SNAKE_CASE` | Tunable parameters | `DISPUTE_WINDOW_DAYS` |

Identifiers are never reused. A retired rule keeps its identifier and is marked as retired.

### Secrets and data in a public repository

This repository is public. Documentation and code MUST NOT contain:

- Credentials of any kind: access keys, API keys, tokens, or passwords.
- Infrastructure identifiers of the organizers, such as bucket names or account IDs. Refer to them through environment variables (see `.env.example`).
- Rows copied from the supplied dataset. Documents report aggregates only; examples use placeholders such as `TXN-...`.

Local secrets live in `.env`, which is ignored by git. Before each push, check that no secret or data file is staged.

### Data provenance labels

Following the challenge's data boundaries, every dataset or example referenced in these documents is labeled as one of:

- **Supplied (synthetic)**: data provided by the organizers (the LATAM Bank dataset).
- **Team-generated**: data we created, such as evaluation conversations and Portuguese cases.
- **Test fixture**: small, clearly labeled data used only to demonstrate a behavior, such as update correctness.
