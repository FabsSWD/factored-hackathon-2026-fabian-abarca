## 1. Purpose

This document defines the evaluation set of policy §16 (M17); M18 runs it and reports the metrics. The supplied escalation labels carry no learnable signal, so evaluation labels come from the policy itself.

There are two kinds of cases, and each one states which it is in `data_source`:

- **`seeded`.** The records are written from a specification as synthetic `SEED-` rows.
- **`real`.** The case points at a real customer and a real transaction of the supplied data, and those records are only ever read.

For both kinds, the label comes from running the Policy Engine on the records and the specified final slots. It never comes from the conversation text or from a model.

## 2. Scenario specifications

The specifications are the versioned source of truth, kept in `config/eval_scenarios/` (version in `version.yaml`):

- **Seeded cases** are in `cases_*.yaml`. They are generated by `scripts/generate_scenarios.py` from archetypes with a seeded random generator, so the same seed writes the same files.
- **Real cases** are in `local/real_cases.yaml`, which is git-ignored. The repository keeps only `real_selection.lock` (section 5).

A seeded specification holds:

- **Records:** one customer (status, country, age band, gender, segment), their products and transactions, and earlier cases when a rule needs them (`ESC-02`, `GATE-11`). Amounts are in the transaction currency, and dates are `days_ago` relative to `BUSINESS_DATE`. A transaction marked `foreign` belongs to another seeded customer (`GATE-04`).
- **The customer's true intent:** the disputes in order. Each dispute names the transaction it is about and the final values of its slots (reason, card in possession, shared credentials, expected amount, delivery date, merchant contacted, fee, duplicate twin). It also holds the answer to the card block offer and the final answer to the summary.
- **Special conditions:** no session, a refusal to authenticate, exhausted authentication attempts, an unsupported language, injection attempts, a request for a human, legal or vulnerability signals, an expired session, an unclear confirmation, both models unavailable, a failed action, and a question never answered.
- **The customer script for M18:** a first message and one prepared answer for each question the assistant may ask, keyed by the trace's reply kind (`transaction_ref`, `reason_code`, `block_offer`, `summary`, `confirmation`, `authentication`, and so on), plus side questions. The wording varies: exact or approximate amounts, a day, a range or "ayer", the merchant by name or by kind, side questions and unclear answers.

Seeded identifiers derive from the case number and always carry the `SEED-` prefix: customer `SEED-C007`, product `SEED-P007-card`, transaction `SEED-T007-t1`, earlier case `SEED-D007-1`, document number `SEED-0007`.

## 3. Reference labels

`app/evaluation/labeler.py` runs the `DeterministicPolicyEngine` on each case (policy §16.2). For each dispute it builds the `PolicyRequest` that the conversation ends with when the customer gave the final values and the conditions held:

- **Session, flags and counters.** These are the ones the conditions imply. For example, the strike count at the limit together with the Input Guard result, or the clarification limit reached on the target that was never answered.
- **Signals.** They are derived from the intended extraction, except that they are `unavailable` when both models are down.
- **Records.** These are the ones the Tool Layer reads. A seeded case reads its specification. A real case reads the database (section 5).
- **What one dispute leaves for the next:** the case it created, a card it blocked, and an unrecognized transaction counted for `ESC-03`.

The label stores, per dispute: the outcome, the triggered rules, the failed gates, the queue, the priority, the inform reason, the tier, and the actions the conversation must execute (ACT-03 when the block is confirmed, ACT-02 and ACT-04 on RESOLVE, ACT-05 on ESCALATE). The conversation ends at the first escalation.

**What the labels measure.** The labels come from the same engine the system uses (§16). The evaluation therefore measures whether the full pipeline reaches the right engine inputs: it extracts the right slots, identifies the right transaction, asks what it must ask, and calls the tools. It does not validate the engine against the policy, because a mistake in the engine would appear in both the system and the label. That independent check is the human review of the sample (section 8), where a person compares each label with the policy text.

Where the labels are kept:

- **Seeded labels** are in `labels.yaml`, written by `scripts/label_scenarios.py`. A test recomputes them. The generator also labels every case while it writes it, and fails if a specification does not give the outcome and rule its archetype intends.
- **Real labels** are in `local/real_labels.yaml`, written with their selection. The expected label of each case key is also in `real_selection.lock`, without identifiers.

## 4. Seeded records

`scripts/seed_scenarios.py` materializes the seeded specifications as `SEED-` rows. Real cases are never seeded.

- **Owner role only.** The script runs only with `MIGRATION_DATABASE_URL` (the owner role). It refuses a URL with the application's user, and checks that the connected user owns the Core Banking tables.
- **Synthetic rows only.** Every row is synthetic, prefixed `SEED-`, and carries lineage `seed:scenarios@<version>`. Each customer's document number is stored as its HMAC, so M18 logs in through the real Identity Service with the document and the test OTP.
- **Segments.** Customers are spread over the countries and age bands of the supplied data (Colombia, México and Argentina; six age bands; three genders) for the segment analysis of M18. Cases in Portuguese belong to customers in those countries, because the data has no Brazilian customers and no BRL.
- **Idempotent, with the audit trail untouched.** Seeding again puts every case back in the state of its specification:
  - The cases, card blocks, handoffs and OTP challenges left by earlier runs on `SEED-` customers are removed.
  - Their sessions are revoked (`revoked_at`), never deleted.
  - `audit_logs` is never touched, because the audit trail is append-only. A test checks that re-seeding changes no audit row.
- **Clean removal, unless there are traces.** `--remove` deletes every `SEED-` row and nothing else. If audit records point to sessions of `SEED-` customers, it refuses and removes nothing: the audit trail is append-only, so seeded customers with traces stay by design. To start from scratch, use a new database. The error message says the same.
- **Protected from the loader.** The Core Banking loader never inserts a `SEED-` row from a file and never overwrites a row with `seed:` lineage.
- **Fixed business date.** The scripts name dates relative to business date 2026-06-17, so seeding refuses any other `BUSINESS_DATE`.

## 5. Cases on real records

`scripts/select_real_scenarios.py` selects 22 cases anchored in real customers and transactions and labels them.

- **Read-only and local.** The script reads with `DATABASE_URL` (the application role) inside a read-only transaction, and never writes a row.
- **Deterministic selection.** Each category takes the records that meet its criteria, ordered by `md5(seed || transaction_id)` with seed `20261004`, one case per customer.
  - Customers with any case or card block are skipped, so state left by manual tests or M18 runs never enters the selection.
  - Records are kept away from the window edges.
  - A record the customer describes in words must be alone within two days, and the description must identify exactly that record under the GATE-05 rule. The script checks this.
- **Label from the engine on the real records.** The records read are the ones `transaction_candidates` reads: the customer, their products and cases, the transactions within `LATE_WINDOW_DAYS`, and the transaction itself when the customer names it by reference. The selection fails if a label is not the one its category intends, as the generator does for seeded cases.
- **Identifiers stay local.** The dataset is privately distributed, and since M11 no versioned file may hold a customer or transaction identifier.
  - The selected cases (identifiers, final slots and script) and their labels are written to `config/eval_scenarios/local/`, which is git-ignored.
  - The script's placeholders (`{transaction}`, `{reference}`) are filled from the record at run time (`app.evaluation.real.render_script`). No amount, merchant or date is stored, even locally.
  - The identifier test of M11 also scans `config/eval_scenarios/` outside `local/`.
- **The lock.** The repository keeps `config/eval_scenarios/real_selection.lock`. It holds:
  - the version of the criteria and the seed;
  - the business date;
  - the count per category and language;
  - the expected label of each case key (`R001`...);
  - `ids_sha256`: the SHA-256 of the lines `<case key> <customer_id> <transaction_id>`, ordered by key.

  The lock is written once. `--check` selects again and compares the hash and the labels with the lock. If anything differs, the script writes nothing and lists what changed by case key, never by identifier. The split, the mix and the review sample read the case keys and the lock, so they are reproducible from the repository without the database.
- **The document number is never stored.** M18 reads it from `data/raw/customers.csv` by `customer_id` when it logs in (`document_for`). It never goes into a YAML file or a report.

| Category | Cases (es / pt) | Label |
|---|---|---|
| Unrecognized card purchase, T1 | 3 / 2 | `RESOLVE` T1 |
| Unrecognized card purchase, T2 | 2 / 1 | `RESOLVE` T2 |
| Pending, declined, reversed purchase | 3 / 3 | `INFORM` (GATE-06) |
| Older than the late window, named by its reference | 1 / 1 | `INFORM` outside window (GATE-08) |
| Late filing | 1 / 1 | `ESCALATE` `ESC-07` |
| Another customer's transaction, by reference | 1 / 1 | `REFUSE` (GATE-04) |
| Deposit disputed as unrecognized | 1 / 1 | `INFORM` not disputable (GATE-07) |

## 6. Case mix

There are 116 cases: 94 seeded and 22 real. By language, 62 are in Spanish, 53 in Portuguese and 1 in English (`GATE-01`). They cover the three paths the challenge asks for:

| Path | Seeded | Real | Final outcomes |
|---|---|---|---|
| Normal resolution | 35 | 8 | `RESOLVE` |
| Ambiguous or unsupported request | 29 | 12 | `INFORM`, `REFUSE`, `ESC-09`, `ESC-12`, `ESC-14` |
| Needs human intervention | 30 | 2 | `ESCALATE` on the other triggers |

- **Every rule covered.** Every gate (`GATE-01` to `GATE-11`) fails in at least one case and every trigger (`ESC-01` to `ESC-14`) fires in at least one.
- **Flows without real data.** These flows appear only on seeded records: `RC_DUPLICATE`, `T3` purchases, `fraud_score` above 35, and the special conditions.
- **Full counts.** `reports/m17_mix.json` has the counts by source, outcome, rule, gate, language and split, with the real, seeded and Portuguese cases also reported apart.

## 7. Split

The split was fixed before any prompt, threshold or model tuning (policy §16.4), and is kept in `config/eval_scenarios/split.yaml`. It was redone once, to add the real cases, and is pinned again.

| Split | Cases | Real | Portuguese | Use |
|---|---|---|---|---|
| Calibration | 37 | 7 | 17 | M7 only: the cases thresholds may be fitted on |
| Evaluation | 79 | 15 | 36 | M18: never used to set a `Calibrated` parameter |

- **How it is built.** It is stratified by data source, language and path, with seed 20261002. Every rule and failed gate keeps at least one case in evaluation.
- **Case keys only.** Real cases enter the split by their keys (`R001`...) and the labels in the lock, never by an identifier, so the fingerprint is reproducible from the repository.
- **Pinned.** A test pins the split's fingerprint, so any change fails, and `scripts/label_scenarios.py` refuses to overwrite it.

## 8. Human review

`python scripts/label_scenarios.py --review` writes `reports/m17_review/review_sample.csv`. The sample has 50 cases, the minimum of policy §16.3 (at least 10%, minimum 50):

- every `ESC-03`, `ESC-06` and `ESC-13` case;
- 15 real cases, one of each category first;
- the rest of the seeded cases, stratified by path and language.

Real rows show the records read from the database for the cases in `local/`, so the file is derived data. It is git-ignored and never committed. It holds no customer or transaction identifier (a reference the customer quotes appears as `[reference]`) and no document number. A test checks the sample selection and the rows without the database.

Each row shows:

- the records;
- the intent and final slots;
- the special conditions;
- the first message;
- the expected outcome, rules, failed gates, queue, priority and actions;
- the policy sections that apply.

Two columns are left for the reviewer's verdict and notes. This review is the independent validation of the engine against the policy (section 3).

Disagreements are resolved by fixing the specification, or, if the policy is unclear, by amending the policy and bumping its version (§16.3).

## 9. Notes for M18

- **Fault injection.** `ESC-10` and `ESC-11` need fault injection in the harness, because the conversation cannot cause them:
  - `ESC-10`: the Tool Layer write of ACT-02 fails after its retries.
  - `ESC-11`: OpenAI and Kev are both down.

  Their labels assume those faults (`tool_failure`, `models_unavailable`).
- **Separate metrics.** Metrics are reported for real and seeded cases separately, as well as together.
- **Real customers keep what a run creates.** A run on real cases writes cases (ACT-02) and audit records on real customers. M18 must remove the cases it created there and record that it did, and must not touch `audit_logs`. Run `scripts/select_real_scenarios.py --check` before a run: after one, those customers have cases and a fresh selection skips them.

## 10. Limitations

- **Labels assume the intended slots.** A reference label assumes the conversation ends with the intended slot values. A wrong extraction in M18 is an error of the system under test, not of the label.
- **A single customer script.** The scripts are prepared answers. If a conversation asks something unforeseen, the script has no answer, and M18 must count that as a failed conversation, not as a label error.
- **Fixed business date and Portuguese segments.** Dates in the scripts and the real labels assume business date 2026-06-17. Portuguese cases use the countries and currencies of the supplied data.
- **Real labels are a snapshot.** A real label depends on the state of the database when it was selected. The selection skips customers with cases or blocks, and `--check` detects any drift.
- **Real cases cover fewer rules.** The real cases cover GATE-04, GATE-06, GATE-07, GATE-08, `ESC-07` and `RESOLVE` in T1 and T2. The other rules are evaluated only on seeded records. The real cases decline the card block, so ACT-03 runs only on seeded customers.
